# 压测报告（benchmark）

> 本文件是简历里所有性能数字的**唯一来源**。数字必须自己跑，机器配置必须如实写。
> 面试官会追问「你这个数字怎么测的」——第 3 节就是答案，第 8 节是这套数据的可信度边界。
> 最后更新：2026-11-12，代码版本 `27a1cee`（连接池分摊改动在其后，见第 7 节）。

---

## 1. 环境

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 7745HX（8 核 16 线程）/ 15.3GB / Windows 11 |
| 应用 | 本地 `.venv` 直跑 `uvicorn --workers 1`（宿主机，非容器） |
| 中间件 | PostgreSQL 16 + Redis 7，Docker Desktop，端口映射到本机 |
| 代码版本 | `27a1cee` |
| 数据 | 单表 `links` 100,010 行，`code` 唯一索引，数据集可全部放进 PG 缓冲池 |
| 缓存 | L1 `TTLCache(maxsize=10000, ttl=30s)` / L2 Redis `TTL=3600s` |
| 连接池 | `pool_size=20, max_overflow=10, pool_pre_ping=True, pool_recycle=1800` |
| 压测工具 | locust 2.47，200 并发，spawn rate 20，持续 3 分钟 |
| 每轮前置 | `redis-cli flushdb` → 重启服务 → 预热 5000 个热点码 → 开跑 |

locust 与服务同机竞争 CPU，压测时宿主机剩余内存约 2.8GB。**这是本机压测，不是云上压测**，
数字只用于「组间对比」，不代表生产容量。

## 2. 数据集与访问分布

| 项 | 值 |
|---|---|
| 短链总数 | 100,000（`bench/seed.py 100000 5000`） |
| 热点码 | 5,000（占总量 5%） |
| 热点请求占比 | 80%（`BENCH_HOT_RATIO=0.8`） |
| 长尾请求占比 | 20% |

**为什么不用均匀随机**：均匀打 10 万条、L1 只有 1 万容量时，LRU 命中率上限就是
`10000/100000 = 10%`，缓存价值被容量稀释，测出来的数字没有意义。
真实短链流量是幂律分布（少数链接吃掉大部分点击），80/20 才是要测的场景。

## 3. 执行步骤

五组一把梭，避免手工开五个终端把变量搞乱：

```powershell
docker compose up -d postgres redis
uv run python bench/seed.py 100000 5000              # 只做一次
uv run python bench/run_all_groups.py --port 8001 --users 200 --duration 3m
```

脚本对每组固定做五件事，顺序不能改：

1. 探 `/healthz`：端口有旧进程就拒绝开跑；
2. `redis-cli flushdb`：不清的话下一组白占上一组的缓存；
3. 用该组开关重启服务（环境变量优先级高于 `.env`）；
4. 预热 5000 个热点码：不预热的话前 30 秒全是冷启动，整组数据被污染；
5. locust 跑 3 分钟 → 落 CSV → 抓 `/metrics` 快照 → 停服务 → 冷却 30 秒。

**三个必须知道的坑**（都是这次真踩的）：

- **代理**：环境里有 `HTTP_PROXY=127.0.0.1:56475`（本机加速器留下的），`NO_PROXY` 是空的。
  locust / prewarm 默认读环境代理，于是 `127.0.0.1:8000` 的请求也被代理转发：
  吞吐被吃掉、代理一抖就是成批 `status 0`、`/metrics` 直接 502。
  现在压测脚本给所有子进程注入 `NO_PROXY=127.0.0.1,localhost,::1`，`loadtest.py` 里关掉 `trust_env`。
- **端口**：上一组 uvicorn 没杀干净，或另有一个终端在跑同一套压测，两组数据会互相串味。
- **顺序漂移**：同一份配置，**后跑的那次更快**（文件缓存 / PG 缓冲池预热），实测 A/B/C 三组第二次都比第一次快 10% 左右。
  所以本报告给出的都是区间，不是单点值。

## 4. 五组配置

| 组 | 场景 | L1 | L2(Redis) | singleflight | 埋点 | 想验证什么 |
|---|---|---|---|---|---|---|
| A | 纯数据库 | ✗ | ✗ | ✗ | ✗ | 基线：所有请求都打 PG |
| B | + Redis | ✗ | ✓ | ✗ | ✗ | 一级缓存能带来多少提升 |
| C | + L1 进程内 | ✓ | ✓ | ✗ | ✗ | 省掉 Redis 的 TCP 往返值多少 |
| D | + singleflight | ✓ | ✓ | ✓ | ✗ | 削缓存失效瞬间的回源尖峰 |
| E | + 埋点旁路 | ✓ | ✓ | ✓ | ✓ | 一次 Redis INCR 的代价 |

> A–D 组统一关掉埋点，E 组才打开，这样 E−D 的差值就是「一次 `INCR`+`EXPIRE` 的代价」，
> 否则变量不干净，数字解释不清。

## 5. 结果（200 并发 / 3 分钟 / 单 worker）

| 组 | QPS（两次） | P50 | P95 | P99 | 错误率 | L1 命中率 | 回源 DB 次数 | 回源 DB/秒 |
|---|---|---|---|---|---|---|---|---|
| A 纯 DB | 566 / 631 | 310–340ms | 370–440ms | 400–500ms | 0% | — | 106,732 | **593** |
| B +Redis | 722 / 773 | 250–260ms | 300–330ms | 320–360ms | 0% | — | 26,938 | **150** |
| C +L1 | 719 / 804 | 240–270ms | 290–340ms | 310–370ms | 0% | 61.1% / 62.9% | 26,604 | **148** |
| D +singleflight | 678 | 280ms | 350ms | 370ms | 0% | 60.0% | 25,350 | **141** |
| E +埋点 | 635 | 300ms | 380ms | 410ms | 0% | 58.8% | 24,466 | **136** |

- 「回源 DB 次数」= `cache_lookups_total{layer="l2",result="miss"}`，是应用内计数器，**不吃机器噪声**。
  A 组没有缓存，取 `http_requests_total`。
- B 组 L2 命中率 80.0%（107,878 / 134,816）；C/D/E 的分母是「L1 未命中之后再查 Redis」，口径不同，别横向比。
- D、E 只有一次采样，因为它们的结论不依赖 QPS（见 6.4、6.5）。

### 缓存收益：用计数器说话，不用 QPS 说话

| 指标 | A | B | 变化 |
|---|---|---|---|
| 回源 PG 次数/秒 | 593 | 150 | **−74.7%** |
| 平均延迟 | 325ms | 255ms | −21.5% |
| QPS | 566–631 | 722–773 | +22%~+31% |

**这是整份报告里最硬的一组数字**：它来自进程内计数器，不是采样，也不受机器冷热影响。
QPS 的百分比落在噪声带里（见第 8 节），只作参考。

## 6. 归因（每一句都能被数据打脸或证实）

### 6.1 先说清方法论：这是闭环压测，测的是延迟不是容量

locust 200 用户是**闭环**模型——每个用户拿到响应才发下一个请求，因此
`QPS ≈ 用户数 / 平均延迟`。实测 A 组 200/0.325 ≈ 615（实测 566–631）、B 组 200/0.255 ≈ 784（实测 722–773），
对得上。**所以「QPS 提升」和「延迟下降」在这套数据里是同一件事的两种写法。**

更直接的证据：同一份 A 组配置，30 并发时 628 QPS / P50 44ms，200 并发时 566 QPS / P50 340ms。
并发涨 6.7 倍，吞吐没动，延迟涨 7.7 倍——系统在 **600~700 QPS 附近就饱和了**，之后加的全是排队。

**饱和点在哪**：单 worker = 1 个事件循环 + anyio 默认 40 个线程跑同步 `def` 路由 + SQLAlchemy 20 个连接。
三层队列叠加，200 并发下排队时间占了 P50 的八成。

### 6.2 A → B：Redis 是这批改动里唯一的大头

- 回源 PG 从 **593 次/秒降到 150 次/秒（−74.7%）**，L2 命中率 80%。
- 延迟从 325ms 降到 255ms。
- 为什么降不到更低：剩下 20% 是长尾码，10 万个码里 9.5 万个本来就冷，
  这部分回源是架构固有成本，不是没优化好。**这一条也是后面「布隆过滤器挡不存在码」的动因。**

### 6.3 B → C：L1 命中 61%，吞吐看不出来，但下游被卸掉了

- QPS 722/773 → 719/804，**差异在噪声内**（两次跑自己就差 12%）。
- 但 Redis 调用量从每轮 134,816 次降到 52,298 次（**−61%**）。
- **结论要敢说**：瓶颈是线程池排队而不是网络 RTT，所以 L1 提升不了吞吐；
  它的价值是**卸载下游**（Redis 连接数、序列化、网络往返）。
  > 谁的报告里 L1 让 QPS 翻倍，先怀疑他上一组没清缓存。

### 6.4 C → D：singleflight 在 80/20 流量下 0 次合并

- `singleflight_total{result="leader_ok"} 25350`，`result="shared"` **一条都没有**。
- QPS 678，比 C 低 6%（噪声内）：多一层锁和字典查找，没人受益。

原因：80/20 流量下每个冷码的未命中窗口只有几毫秒，200 并发撞上同一个冷码的概率极低。
**原始手册里「D 组只看 P99 不看 QPS」的说法，真相是这负载下它根本触发不了。**

要验证它有用，得单独造场景（`bench/stampede.py`：钉死一个码 + L1 TTL 1 秒 + 关掉 L2，200 并发，60 秒）：

| 场景 | 回源 DB 次数 | singleflight 合并次数 | DB 查询/秒 |
|---|---|---|---|
| 关单飞 | 604 | 0 | 10 |
| 开单飞 | **60** | 677 | **1** |

**回源压降 89.9%**：每次缓存失效，回源从平均 10 次并发查询压到 1 次。
singleflight 是**防击穿**组件，不是提吞吐组件——这句话现在有数据。

### 6.5 D → E：埋点的代价 < 10%，换来的是不丢数

- QPS 678 → 635（−6.3%），P99 370 → 410ms，P50 +20ms。
- 代价来源：每次跳转多一次 Redis pipeline（`INCR` + `EXPIRE`），在饱和状态下换成排队时间。
- **这个 −6.3% 落在噪声带里，只能说「代价在 10% 以内」，不能说「精确 6.3%」。**
- 换来的是：缓存命中时不再漏记（原先 20 次点击只落 1 条），跳转路径上不再 `INSERT+COMMIT`。
  如果仍同步写库，E 组会退化到 A 组的量级——这才是埋点旁路真正的价值。

## 7. 多 worker 容量验证（C 组配置，`--workers 4`）

| 项 | 1 worker | 4 workers（修复前） | 4 workers（修复后） |
|---|---|---|---|
| QPS | 719–804 | 1538 | 1457 |
| P50 | 240–270ms | 67ms | 71ms |
| P99 | 310–370ms | 130ms | 140ms |
| 错误 | 0 | **18 次异常 / 5 个 500** | **0** |
| 每 worker 连接池 | 20 + 10 | 20 + 10（超限） | **5 + 2** |

**修复前踩的坑**：`4 × (20 + 10) = 120 > PG max_connections=100`，日志报
`FATAL: sorry, too many clients already`。修法是把连接池额度按 `WEB_CONCURRENCY` 均分
（`app/db.py`），每进程 `20/4 = 5`，`/metrics` 里 `db_pool_size` 直接能看到 5。

**2 倍而不是 4 倍**：闭环模型下 200 用户已经被榨干（P50 71ms，理论上限 200/0.071 ≈ 2817 QPS），
这时瓶颈转移到了**压测机自己**（locust 单进程 + 同机抢 CPU）。要测 4 worker 的真实上限，
得把 locust 放到另一台机器上跑，或改用 open-loop 的恒定速率模式。

## 8. 这份数据的可信度边界（面试被追问就靠它）

- **能信**：回源次数、命中率、singleflight 的 leader/shared 计数、错误数、`db_pool_size` —— 这些是应用内计数器，确定值。
- **只能看区间**：QPS 与分位数。同配置重复跑的差异 **10%~12%**（C 组 719 vs 804；A 组 566 vs 631；B 组 722 vs 773），
  且**后跑的快**（系统预热漂移）。所以 **< 15% 的差异一律不当作结论**。
- **组间顺序有偏**：五组是顺序跑的，越往后机器越热。要精细比较，正确做法是交错执行（A B C D E E D C B A）取均值。
  这一点写在这里，是因为它比「编一个好看的数字」重要。
- **唯一一次数据作废**：早期那批被环境代理污染（见第 3 节），已整体重跑，不留半成品。

## 9. 结论

- 单机单 worker，200 并发：**700 QPS 量级 / P99 300~400ms / 0 错误**；4 worker 约 **1.45k QPS**，错误 0。
- 缓存收益（计数器口径，无噪声）：**回源 PG 从 593 次/秒降到 150 次/秒，−74.7%**，L2 命中率 80%。
- L1 命中 61%，吞吐上无感，但把 Redis 调用量砍掉 61%——**卸载下游，不是提吞吐**。
- singleflight 在常规流量下 0 合并；定向尖峰场景回源 **−89.9%**（604 → 60）。
- 埋点旁路成本 **< 10% QPS**，换来统计不丢数。
- 当前瓶颈：**单 worker 的同步阻塞模型**（线程池排队），不是 PG、不是 Redis、不是网络。
- 下一步（按性价比）：① 多 worker 横向扩（已验证 2 倍，需解决压测机瓶颈）；
  ② `def` 路由改 `async def` + asyncpg，彻底摆脱线程池；③ 长尾回源加布隆过滤器，把不存在的码挡在 DB 之前。

## 10. 复现方式

```powershell
docker compose up -d postgres redis
uv run python bench/seed.py 100000 5000
uv run python bench/run_all_groups.py --port 8001 --users 200 --duration 3m    # A~E
uv run python bench/run_all_groups.py C --port 8001 --workers 4 --tag _w4      # 多 worker
uv run python bench/stampede.py --port 8001                                    # 单飞定向验证
uv run python bench/summarize.py                                               # 汇总成表
```

原始数据：`bench/out/<组>_stats.csv`（locust）、`<组>_metrics.txt`（应用侧指标）、
`<组>_uvicorn.log`（服务端访问日志，每轮几十 MB，用完即删，重跑一次就有）。
带 `_r2` 后缀的是重复跑，带 `_w4`/`_w4b` 的是多 worker 跑（`_w4b` 为连接池修复后）。
