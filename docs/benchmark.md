> 面试官会问「你这个数是怎么测的」，第 3 节写的就是这个，第 8 节写了哪些数能信、哪些只能看区间。
> 数据采集于 2026-11-12，代码版本 `27a1cee`（连接池分摊的改动在这之后，见第 7 节）。

> 所以下面所有数字仍然是 11-12 那批。复跑也没有覆盖旧数据：失败那次把 `bench/out/C_stats.csv` 冲掉了，

## 1. 机器和环境

| 项 | 值 |
|---|---|
| 机器 | AMD Ryzen 7 7745HX（8 核 16 线程）/ 15.3GB / Windows 11 |
| 应用 | 本地 `.venv` 直跑 `uvicorn --workers 1`（宿主机上跑，没放容器里） |
| 中间件 | PostgreSQL 16 + Redis 7，Docker Desktop，端口映射到本机 |
| 代码版本 | `27a1cee` |
| 数据 | 单表 `links` 100,010 行，`code` 唯一索引，整个数据集能放进 PG 缓冲池 |
| 缓存 | L1 `TTLCache(maxsize=10000, ttl=30s)` / L2 Redis `TTL=3600s` |
| 连接池 | `pool_size=20, max_overflow=10, pool_pre_ping=True, pool_recycle=1800` |
| 压测工具 | locust 2.47，200 并发，spawn rate 20，跑 3 分钟 |
| 每轮前置 | `redis-cli flushdb` → 重启服务 → 预热 5000 个热点码 → 开跑 |

locust 和服务挤在同一台机器上抢 CPU，跑的时候宿主机只剩 2.8GB 左右内存。
全是本机压测，没上云，这批数只能拿来比组间高低，不能当生产容量用。

## 2. 数据是怎么造的

| 项 | 值 |
|---|---|
| 短链总数 | 100,000（`bench/seed.py 100000 5000`） |
| 热点码 | 5,000，占总量 5% |
| 热点请求占比 | 80%（`BENCH_HOT_RATIO=0.8`） |
| 长尾请求占比 | 20% |

一开始也想过均匀随机打这 10 万条，算了一下不行：L1 只有 1 万容量，
`10000/100000 = 10%` 就是 LRU 命中率的天花板，缓存的价值被容量摊薄，测出来什么都说明不了。
真实短链流量是幂律的，少数链接吃掉大部分点击，所以按 80/20 打。

## 3. 我是怎么跑的

A 到 E 五组一次跑完，不想手工开五个终端，环境变量容易搞错。F 组是后来加的，单独跑。

```powershell
docker compose up -d postgres redis
uv run python bench/seed.py 100000 5000              # 只做一次
uv run python bench/run_all_groups.py --port 8001 --users 200 --duration 3m
```

脚本对每组固定走这几步，顺序不能改：

1. 探 `/healthz`，端口上有旧进程就不让开跑；
2. 真打一次 `/{code}`，要求返回 302。`/healthz` 不查库，PG 挂了它照样 200，11-17 就是栽在这；
3. `redis-cli flushdb`，不清的话这一组白蹭上一组的缓存；
4. 用该组开关重启服务（环境变量优先级高于 `.env`）；
5. 预热 5000 个热点码，不预热的话前 30 秒全是冷启动，整组数据就脏了；
6. locust 跑 3 分钟，落 CSV，抓 `/metrics` 快照，停服务，冷却 30 秒；
7. 每组跑完看 `stats.csv` 的失败数和 P50，不达标直接退出，别让人拿废数据去写报告。

踩过三个坑，都记在这：

- 代理。环境里有 `HTTP_PROXY=127.0.0.1:56475`（本机加速器留下的），`NO_PROXY` 是空的。
  locust 和 prewarm 默认读环境代理，于是打到 `127.0.0.1:8000` 的请求也被转了出去：
  吞吐被吃掉一块，代理一抖就是成批 `status 0`，`/metrics` 直接 502。
  现在压测脚本给所有子进程注入 `NO_PROXY=127.0.0.1,localhost,::1`，`loadtest.py` 里关掉 `trust_env`。
- 端口。上一组 uvicorn 没杀干净，或者另开一个终端在跑同一套脚本，两组数据会互相串味。
- 顺序漂移。同一份配置，后跑的那次更快，因为文件缓存和 PG 缓冲池都是热的，
  A/B/C 三组第二次都比第一次快 10% 左右。所以这里给的都是区间，没有单点值。

## 4. 六组配置（F 组还没跑）

| 组 | 场景 | L1 | L2(Redis) | singleflight | 埋点 | 限流 | 想验证什么 |
|---|---|---|---|---|---|---|---|
| A | 纯数据库 | ✗ | ✗ | ✗ | ✗ | ✗ | 基线，请求全打 PG |
| B | + Redis | ✗ | ✓ | ✗ | ✗ | ✗ | 一级缓存能带来多少提升 |
| C | + L1 进程内 | ✓ | ✓ | ✗ | ✗ | ✗ | 省掉一次 Redis TCP 往返值多少 |
| D | + singleflight | ✓ | ✓ | ✓ | ✗ | ✗ | 削缓存失效瞬间的回源尖峰 |
| E | + 埋点旁路 | ✓ | ✓ | ✓ | ✓ | ✗ | 一次 Redis INCR 的代价 |
| F | C + 限流 | ✓ | ✓ | ✗ | ✗ | ✓ | 跳转路上多一次 Redis EVAL 的代价 |

A 到 D 组埋点统一关着，只有 E 打开，这样 E 减 D 的差值才好说是「一次 `INCR` + `EXPIRE`」的代价。
不这么配变量不干净，数字解释不清。

限流在 A 到 E 一律关掉：压测请求全从 127.0.0.1 出来，按 IP 限流一开，跑不了几百个请求就全是 429。
这个坑第一次跑压测就踩过。

F 组是后来加进代码的，配置和 C 一样，只多开限流，阈值拉到 1 亿（`RATE_LIMIT_REDIRECT_PER_MIN=100000000`），
保证不会真触发 429，纯粹为了量那一次 Lua EVAL。这组还没跑，结果待补。

## 5. 结果（200 并发 / 3 分钟 / 单 worker）

| 组 | QPS（两次） | P50 | P95 | P99 | 错误率 | L1 命中率 | 回源 DB 次数 | 回源 DB/秒 |
|---|---|---|---|---|---|---|---|---|
| A 纯 DB | 566 / 631 | 310–340ms | 370–440ms | 400–500ms | 0% | 无 | 106,732 | 593 |
| B +Redis | 722 / 773 | 250–260ms | 300–330ms | 320–360ms | 0% | 无 | 26,938 | 150 |
| C +L1 | 719 / 804 | 240–270ms | 290–340ms | 310–370ms | 0% | 61.1% / 62.9% | 26,604 | 148 |
| D +singleflight | 678 | 280ms | 350ms | 370ms | 0% | 60.0% | 25,350 | 141 |
| E +埋点 | 635 | 300ms | 380ms | 410ms | 0% | 58.8% | 24,466 | 136 |

F 组没有数据，这张表里不占行。

「回源 DB 次数」取的是 `cache_lookups_total{layer="l2",result="miss"}`，应用内计数器，不吃机器噪声。
A 组没有缓存，用的是 `http_requests_total`。
B 组 L2 命中率 80.0%（107,878 / 134,816）。C、D、E 的分母是「L1 没命中之后才去查 Redis」，
口径不一样，别横向比。D、E 只跑了一次采样，它们要说的事不靠 QPS 撑着（见下面 C→D、D→E 两节）。

### 缓存到底省了多少：看计数器，别看 QPS

| 指标 | A | B | 变化 |
|---|---|---|---|
| 回源 PG 次数/秒 | 593 | 150 | −74.7% |
| 平均延迟 | 325ms | 255ms | −21.5% |
| QPS | 566–631 | 722–773 | +22%~+31% |

这组数来自进程内计数器，不是采样，也不受机器冷热影响，所以比 QPS 可信得多。
QPS 那个百分比落在噪声带里（第 8 节），只能当参考。

## 6. 为什么会是这个结果

### 闭环压测意味着什么

locust 200 用户是闭环模型，每个用户拿到响应才发下一个请求，所以 `QPS ≈ 用户数 / 平均延迟`。
拿 A 组验算：200/0.325 ≈ 615，实测 566–631；B 组 200/0.255 ≈ 784，实测 722–773，都对得上。
换句话说，「QPS 提升」和「延迟下降」在这套数据里说的是同一件事。

还有更直接的证据。同一份 A 组配置，30 并发时 628 QPS / P50 44ms，
200 并发时 566 QPS / P50 340ms。并发涨 6.7 倍，吞吐基本没动，延迟涨 7.7 倍，
说明系统在 600~700 QPS 附近就饱和了，后面加的全是排队。

饱和点怎么来的：单 worker 就是一个事件循环，anyio 默认 40 个线程跑同步 `def` 路由，
SQLAlchemy 再压 20 个连接，三层队列叠在一起，200 并发下排队时间占了 P50 的八成。

### A → B：Redis 是这批改动里唯一的大头

- 回源 PG **从 593 次/秒降到 150 次/秒（−74.7%）**，L2 命中率 80%。
- 延迟从 325ms 降到 255ms。
- 为什么降不到更低：剩下 20% 是长尾码，10 万个码里 9.5 万个本来就冷，
  这部分回源是架构固有成本，优化不掉。后来想加布隆过滤器挡不存在的码，动因就在这。

### B → C：L1 命中 61%，吞吐看不出来，Redis 被卸掉一半多

- QPS 722/773 → 719/804，差异在噪声里，两次跑自己就差 12%。我不敢说 L1 提了吞吐。
- 但 Redis 调用量从每轮 134,816 次降到 52,298 次（−61%）。
- 我原本以为 L1 能换成 QPS，实测换不成。瓶颈在线程池排队，网络 RTT 不在关键路径上，
  所以 L1 省下的那点往返时间没变成吞吐，它的价值是把下游卸了：Redis 连接数、序列化、网络往返都少一截。
- 顺带一句，谁的报告里 L1 让 QPS 翻倍，先怀疑他上一组没清缓存。

### C → D：80/20 流量下 singleflight 合并 0 次

- `singleflight_total{result="leader_ok"} 25350`，`result="shared"` 一条都没有。
- QPS 678，比 C 低 6%，在噪声内。多一层锁和字典查找，结果没人受益。
- 原因：80/20 流量下每个冷码的未命中窗口只有几毫秒，200 并发同时撞上同一个冷码的概率极低。
- 手册里原来写「D 组只看 P99 不看 QPS」，实际情况是这负载下它压根触发不了，那句话得改。

要验证它有用，得单独造场景（`bench/stampede.py`：钉死一个码，L1 TTL 1 秒，关掉 L2，200 并发，跑 60 秒）：

| 场景 | 回源 DB 次数 | singleflight 合并次数 | DB 查询/秒 |
|---|---|---|---|
| 关单飞 | 604 | 0 | 10 |
| 开单飞 | 60 | 677 | 1 |

回源压降 89.9%，每次缓存失效，回源从平均 10 次并发查询压到 1 次。
所以 singleflight 是防击穿的，不是提吞吐的，这话现在有数撑着。

### D → E：埋点的代价不到 10%，换来的是不丢数

- QPS 678 → 635（−6.3%），P99 370 → 410ms，P50 多了 20ms。
- 代价来自每次跳转多一次 Redis pipeline（`INCR` + `EXPIRE`），饱和状态下这点活直接换成排队时间。
- 这个 −6.3% 落在噪声带里，我最多敢说「代价在 10% 以内」，说「精确 6.3%」就是自己骗自己。
- 换来的是：缓存命中时不再漏记（原先 20 次点击只落 1 条），跳转路径上不再 `INSERT+COMMIT`。
  如果还同步写库，E 组会退化到 A 组的量级，这才是埋点旁路真正值钱的地方。

### F 组：待补

- 配置同 C，只多开限流，阈值 1 亿，跑起来不会出 429。
- 想量的是跳转路径上多一次 Redis EVAL，在饱和状态下折成多少 QPS、多少延迟。
- 结果留空：待补。

## 7. 多 worker：一次连接池爆掉的经历

C 组配置换 `--workers 4`：

| 项 | 1 worker | 4 workers（修复前） | 4 workers（修复后） |
|---|---|---|---|
| QPS | 719–804 | 1538 | 1457 |
| P50 | 240–270ms | 67ms | 71ms |
| P99 | 310–370ms | 130ms | 140ms |
| 错误 | 0 | 18 次异常 / 5 个 500 | 0 |
| 每 worker 连接池 | 20 + 10 | 20 + 10（超限） | 5 + 2 |

第一次起 4 个 worker 就出事了：`4 × (20 + 10) = 120 > PG max_connections=100`，
日志里 `FATAL: sorry, too many clients already`。修法是把连接池额度按 `WEB_CONCURRENCY` 均分（`app/db.py`），
每进程 `20/4 = 5`，`/metrics` 里 `db_pool_size` 能看到就是 5，错误归零。

只有 2 倍，没到 4 倍。我的判断是 200 用户已经被榨干了：修复后 P50 71ms，理论上限 200/0.071 ≈ 2817 QPS，
实际只跑到 1457，瓶颈已经挪到压测机自己身上（locust 单进程，还跟服务抢同一颗 CPU）。
要测 4 worker 的真实上限，得把 locust 挪到另一台机器，或者换成 open-loop 的恒定速率模式。

## 8. 这些数字能信到什么程度

### 为什么 A 组的 QPS 只能看区间

同一份 A 组配置，两次跑出 566 和 631，差了 12%；C 组 719 和 804，B 组 722 和 773。
而且后跑的那次总是更快，这是系统预热漂移，配置没动过。

所以定一条线：**< 15% 的差异不当结论**。
差 12% 我就说「差不多」，不写「提升了 12%」。这条线是从数据里长出来的。

### 其余边界

- 能信：回源次数、命中率、singleflight 的 leader/shared 计数、错误数、`db_pool_size`。都是应用内计数器，确定值。
- 只能看区间：QPS 和 P50/P95/P99。同配置重复跑的差异 10%~12%，理由见上一节。
- 组间有顺序偏差：五组是顺序跑的，越往后机器越热。要精细比较应该交错执行（A B C D E E D C B A）取均值。
  写在这里，是因为这件事比编一个好看的数字重要。
- 作废过两批数据：早期那批被环境代理污染（第 3 节），11-17 那批是 PG 没起来（开头说过）。都没留着凑数。

## 9. 到此为止的结论

- 单机单 worker，200 并发：700 QPS 量级，P99 300~400ms，0 错误；4 worker 约 1.45k QPS，错误 0。
- 缓存收益按计数器算：回源 PG 从 593 次/秒降到 150 次/秒，−74.7%，L2 命中率 80%。
- L1 命中 61%，吞吐上看不出来，但把 Redis 调用量砍掉 61%，价值在下游卸载。
- singleflight 常规流量 0 合并；定向尖峰场景回源 −89.9%（604 → 60）。
- 埋点旁路成本不到 10% QPS，换来统计不丢数。
- F 组还没跑，限流多一次 Lua EVAL 的代价暂时没有数字。
- 现在的瓶颈是单 worker 的同步阻塞模型（线程池排队），PG、Redis、网络都还松。
- 下一步按性价比排：① 多 worker 横向扩，已验证 2 倍，得先把压测机瓶颈解决掉；
  ② `def` 路由改 `async def` + asyncpg，甩掉线程池；③ 长尾回源加布隆过滤器，把不存在的码挡在 DB 之前。

## 10. 怎么复现

```powershell
docker compose up -d postgres redis
uv run python bench/seed.py 100000 5000
uv run python bench/run_all_groups.py --port 8001 --users 200 --duration 3m    # A~E
uv run python bench/run_all_groups.py C --port 8001 --workers 4 --tag _w4      # 多 worker
uv run python bench/stampede.py --port 8001                                    # 单飞定向验证
uv run python bench/summarize.py                                               # 汇总成表
```

原始数据在 `bench/out/<组>_stats.csv`（locust）、`<组>_metrics.txt`（应用侧指标）、
`<组>_uvicorn.log`（服务端访问日志，每轮几十 MB，用完就删，重跑一次就有）。
`_r2` 后缀的是重复跑，`_w4`/`_w4b` 是多 worker 跑（`_w4b` 是连接池修复之后）。
C 组要注意：`C_stats.csv` 已经被 11-17 那次失败覆盖了，只剩报告里记录的两轮数字。
